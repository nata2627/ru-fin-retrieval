## 0. Ключ HuggingFace. Прочитать до всего остального

**Это самая дорогая ошибка проекта на сегодня: она уже сожгла два часа
квоты впустую.** Секреты Kaggle привязаны к конкретной тетради и **новым
ядром не наследуются**. Без токена скачивание весов с HuggingFace режется
по скорости и может встать намертво — а зависание не ошибка, его не ловит
ни один `try`.

### Как подключить, по шагам

1. Открыть тетрадь, в которой будет прогон.
2. В меню над ячейками: **Add-ons → Secrets**.
3. **Attach secret** → если секрета ещё нет, создать: **Add a new secret**.
   * **Label** — ровно `HF_TOKEN`, латиницей, без пробелов. От имени
     зависит код: он читает именно это имя.
   * **Value** — токен с huggingface.co: **Settings → Access Tokens →
     Create new token**, роль **Read** достаточно.
4. Убедиться, что напротив `HF_TOKEN` стоит галочка **именно в этой
   тетради**. В новой тетради галочку ставить заново.

### Через API секрет не прицепить. Проверено

В клиенте Kaggle **нет поля для секретов вообще**: запрос на сохранение
ядра знает про датасеты, ядра, модели, ускоритель и образ, а слова
`secret` в пакете нет ни разу. Ядро `ru-fin-phase-c`, созданное командой
`scripts/kaggle_run.py run c`, печатает «токен HuggingFace недоступен»
и после того, как `HF_TOKEN` прицеплен к нему мышкой: пуш новой версии
задаёт настройки ядра заново.

Отсюда деление, и оно не по «тяжело — легко», а по тому, нужен ли токен:

* **из браузера**, тетрадью `notebooks/kaggle_phase_c.ipynb` — C0, C1,
  C1ф, C2, C3. Всё, что поднимает языковую модель;
* **через `scripts/kaggle_run.py`** — этап B без ускорителя (C4, плотная
  часть). Веса эмбеддеров он тянет под защитой будильника из
  `gpu_search.py`, и на трёх прогонах 29.09 это уже прошло без токена.

Проверять сборку перед тяжёлым прогоном следует **прогоном без
ускорителя**: тот же код, те же входы, те же импорты, модель не
поднимается, квота GPU не списывается. Именно так поймано, что датасет
уезжал без `split.json`, а `run_phase_c.py` не доезжал вовсе.

Сам токен в этом файле не написан и не будет: `docs/` уезжает
в публичный репозиторий на GitHub, и всякий ключ, попавший туда,
считается скомпрометированным с этой секунды. Токен живёт только
в секретах Kaggle. Если он всё-таки куда-то попал — отозвать
на huggingface.co и выпустить новый, это две минуты.

### Проверка перед запуском

Первой ячейкой, до всего остального:

```python
from kaggle_secrets import UserSecretsClient
import os
os.environ["HF_TOKEN"] = UserSecretsClient().get_secret("HF_TOKEN")
print("токен подключён, длина:", len(os.environ["HF_TOKEN"]))
```

Упало или напечатало `ТОКЕНА НЕТ` — **остановиться и вернуться к шагу 2**.
Не запускать долгий прогон «а вдруг проедет»: не проедет, а квота спишется.

## 1. Сколько осталось бесплатного железа

**Посмотрено в панели 29.09.2026: `14h 24m available of 30h`.**

Квоту через API Kaggle не отдаёт, её видно только глазами: открыть любую
тетрадь, справа панель **Session options** (или значок `<>`), строка
**GPU**. Смотреть **до** каждого запуска — число ниже верно на 29.09
и будет другим завтра.

Куда ушли пятнадцать с половиной часов, по истории ядер:

| ядро | когда | ускоритель | оценка |
|---|---|---|---:|
| `ru-fin` — этап A: генерация 150 вопросов и эмбеддинги шести моделей | 26.09 | GPU | 5,5 ч |
| `export` — выгрузка нарезки | 27.09 | GPU | ~0,5 ч |
| `ru-fin-rerank-only` — переранжирование | 27.09 | GPU | ~1,5 ч |
| прогон B, вставший без токена | 29.09 | GPU | 2 ч впустую |
| `export-chunks-cpu`, `phase-b-cpu`, три прогона `base` | 29.09 | **CPU** | 0 ч |
| не опознано по истории | | | ~6 ч |
| | | **потрачено** | **15,6 ч** |

Шесть часов по ядрам не раскладываются: вероятно, оборванные сессии
и попытки, не дошедшие до сохранения вывода. Вывод практический —
**оценивать расход по панели, а не по своим записям**: собственный учёт
оказался оптимистичнее реальности в полтора раза.

Квота недельная и обновляется целиком; когда именно — видно там же
в панели. План ниже рассчитан так, чтобы уложиться **без** обновления.

Отдельно стоит заметить, что три прогона 29.09 сделаны **без ускорителя**
и не стоили ничего. Это правило, а не случайность: поиск по готовым
матрицам эмбеддингов — перемножение матриц, видеокарта для него не нужна,
а сессия без ускорителя получает больше процессорных ядер.

## 2. Бюджет прогонов

Оценки для T4 ×2, vLLM, AWQ-квантование, fp16. **bf16 на T4 нет** — это
Turing; запуск с `bfloat16` упадёт или деградирует молча.

| прогон | что делает | оценка GPU |
|---|---|---:|
| **C0** замер скорости | `--probe 100`, без генерации | 0,2 ч |
| **C1** обучающая выборка | 12 000 вопросов, Qwen2.5-7B-Instruct-AWQ | 2 ч |
| **C1ф** третий фильтр | учитель смотрит кандидатов BM25 | **4–5 ч** |
| **C2** dev и тест | 700 вопросов, Mistral-7B-Instruct-AWQ | 0,5 ч |
| **C3** судья по пулу | Qwen2.5-14B-AWQ, ~320 запросов × 20 кандидатов | 1–1,5 ч |
| **C4** пересчёт выдач | реранкер по ~790 запросам; плотный поиск — на CPU | 0,3 ч |
| | **итого с полным фильтром** | **8–9,5 ч** |
| | **итого с фильтром глубины 30** | **5,3–5,8 ч** |

**Против 14 ч 24 м это значит вот что.** Полный вариант влезает, но
оставляет меньше шести часов на пересдачу — а пересдача понадобится,
если C0 покажет скорость ниже ожидаемой или сессия оборвётся. Вариант
с глубиной 30 стоит вдвое меньше и оставляет **больше восьми часов
запаса**, то есть допускает переделать любой прогон дважды.

**Берите глубину 30.** Это и так рекомендация следующего раздела,
но при таком остатке она перестаёт быть вопросом вкуса.

### Третий фильтр — самая дорогая строка, и она режется

`filter_by_teacher` прогоняет кросс-энкодер по `--filter-depth` кандидатов
BM25 на каждый вопрос. При значении по умолчанию 100 и 16 000 попыток это
**1,6 млн проходов кросс-энкодера** — на T4 около четырёх-пяти часов.

Фильтр включается ключом `--teacher-filter` и **по умолчанию выключен**.
Лестница урезания, сверху вниз — по мере того, как тает квота:

| вариант | стоимость | что теряем |
|---|---:|---|
| `--filter-depth 100` (полный) | 4–5 ч | — |
| **`--filter-depth 30`** ← рекомендую | **1,3 ч** | почти ничего: вопрос, эталон которого учитель не видит в первых 30 из 30, почти наверняка не увидел бы и в первых 50 из 100 |
| фильтр только на dev и тест | 0,2 ч | обучающая выборка чуть грязнее; на 12 000 примерах это переживаемо |
| без фильтра совсем | 0 ч | остаются два фильтра из трёх — на списывание и на общность; это то, чем пользовались на этапе A |

**При нынешних 14 ч 24 м — глубина 30, обучающая выборка 12 000.**
Расход около 5,5 часа, запаса больше восьми.

Если после C0 окажется, что генерация идёт медленнее, и C1 грозит
вылезти за четыре часа — резать **объём обучающей выборки**, а не фильтр:
разница между 8 000 и 12 000 примеров на дообучении маленькой модели
меньше, чем разница между «обучение состоялось» и «квота кончилась
в середине».

Если квоты вдруг останется меньше шести часов (оборвалась сессия,
пришлось переделывать) — фильтр только на dev и тест, обучающая
выборка 8 000. Это укладывается в три часа.

Что бы ни выбрали — **записать выбор и его причину** в `DECISIONS.md`.
От этого зависит состав обучающей выборки, и через месяц причина забудется.

## 3. Порядок прогонов

Разбито на четыре тетради нарочно: сессия Kaggle живёт до 12 часов,
и обрыв на седьмом часу не должен уносить с собой всё остальное.
**Между прогонами скачивать результат.**

### C0 — замер скорости. Первым, всегда

```
!python run_phase_c.py --probe 100 --out /kaggle/working/probe
```

Печатает вопросов в секунду. **По нему назначается объём C1**, а не
наоборот. Если скорость такая, что 12 000 вопросов не влезают в шесть
часов — уменьшать объём здесь, а не обнаруживать это на восьмом часу.

### C1 — обучающая выборка

```
!python run_phase_c.py --train 12000 --dev 300 \
    --teacher-filter --filter-depth 30 \
    --out /kaggle/working/gen
```

Скачать `train.jsonl`, `dev.jsonl` и отчёт. Проверить глазами десяток
вопросов: три речевых режима должны быть различимы, один из них —
без знака вопроса (короткий поисковый запрос).

### C2 — тест другой моделью

```
!python run_phase_c.py --test 400   # модель теста задана по умолчанию: Vikhr-Nemo-12B \
    --out /kaggle/working/test
```

Модель другого семейства обязательна: иначе тест померит, насколько
ученик выучил стиль своего же генератора. 400 вопросов делятся на
невиданные акты и синтетику для сопоставимости.

### C3 — судья по пулу. **Последним, после C4**

**Порядок в этом списке был неверен, и `make pool` на это натыкается
сразу.** Пул собирается по выдачам всех конфигураций, а выдачи посчитаны
по прежним 211 запросам: из 228 запросов, которым нужен эталон, у 180
выдачи нет ни у одной конфигурации. `make pool` отказывается собирать
лист — и отказывается правильно, потому что пул по неполным выдачам
занижает те конфигурации, которых в нём нет, а по метрикам этого не видно.

Поэтому: **C4 → `make pool` → перезалить датасет запросов вместе
с листом → C3.** Генерацию это не задерживает. Пул нужен только живым
и ручным вопросам; у синтетических dev и теста эталон известен по
построению, и в пул они не попадают вовсе. Значит, плотную часть C4
можно считать параллельно генерации, а не после неё, — она бесплатная.

Пул собирается **на маке**: `make pool`. Он должен включать все девять
конфигураций — иначе новые модели окажутся ущемлены.

```
!python run_phase_c.py --judge --out /kaggle/working/judge
```

Дальше на маке: `python3 scripts/sample_for_human.py` — стратифицированная
выборка 150 пар, заказчица размечает по `docs/ANNOTATION_GUIDE.md`,
потом `python3 scripts/kappa.py`. **Каппа идёт в README числом.**
Если она ниже 0,40 — разметку судьи нельзя пускать в тест, и это надо
обнаружить здесь, а не после обучения.

### C4 — пересчёт выдач

Запросов теперь не 211, а около 790. Старые выдачи к ним не подходят,
и метрики по-прежнему считаются по 162 — четыре теста из-за этого
пропускаются, а не падают.

Плотный поиск и BM25 — **без ускорителя**, это бесплатно. Видеокарта
нужна только реранкеру:

```
!python run_phase_b.py --only base --no-rerank --out /kaggle/working/runs   # CPU
!python run_phase_b.py --only base --out /kaggle/working/runs               # GPU, только ради реранкера
```

## 4. Ловушки

1. **Токен.** См. раздел 0. Проверять в каждой новой тетради.
2. **bf16 на T4 нет.** Только fp16.
3. **Пул до судьи, а не после.** `make pool` на маке, со всеми девятью
   конфигурациями.
4. **Скачивать между прогонами.** Вывод ядра живёт, но подключать его
   следующей тетрадью — лишняя морока и лишний источник путаницы.
5. **Не запускать два прогона на одном аккаунте разом** — они делят
   квоту и мешают друг другу.
6. **Заголовочная цифра появится только после C3.** Сейчас размечено
   108 живых вопросов, и все они про одно Положение 590-П. Разнообразие
   актов принесут пул (217 вопросов, 28 актов) и ручные запросы.
