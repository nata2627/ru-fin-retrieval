# Тяжёлые вычисления на Kaggle: пошагово

## Что и зачем

Три вещи в проекте не помещаются в восемь гигабайт памяти мака:

1. **Генерация синтетических запросов.** Вопросы по фрагментам корпуса пишет
   языковая модель. Локально она отбирает почти пять гигабайт и вместе
   с обработкой корпуса подвешивает систему.
2. **Эмбеддинги корпуса.** Каждый из 61 922 фрагментов надо прогнать через
   модель-энкодер и получить вектор. На маке это 3,5 часа на одну модель
   (замерено: 4,9 фрагмента в секунду), на T4 — минуты.
3. **Переранжирование.** Двести запросов по пятьдесят кандидатов — это десять
   тысяч проходов кросс-энкодера.

Всё это — **разовые операции**. После них поиск работает на ноутбуке без
всякой видеокарты: matrix лежит файлом, а метрики считаются мгновенно.

Работа разбита на два этапа, потому что между ними нужен ручной труд:
запросы, написанные руками, и проверка разметки.

```
этап A на Kaggle          вы на маке              этап B на Kaggle        вы на маке
синтетические запросы  →  50 запросов руками   →  выдачи всех           →  метрики,
эмбеддинги корпуса        проверка разметки        конфигураций            разбор ошибок
```

## Что понадобится один раз

**Подтверждённый телефон в аккаунте Kaggle.** Без этого недоступны ни
видеокарта, ни интернет из ноутбука, а интернет нужен: модели скачиваются
с HuggingFace. Проверить: `kaggle.com` → аватар в правом верхнем углу →
**Settings** → раздел **Phone verification**. Если не подтверждён — подтвердить.

Проверить, что всё доступно, можно прямо в ноутбуке: меню **Settings**
в строке над ячейками. Там три пункта — про интернет, **Accelerator**
и **Environment Preferences**.

Квота видеокарты — около 30 часов в неделю, сессия до 12 часов. Нашим этапам
нужно примерно час и полтора часа соответственно, так что квота не помеха.

## A5. Пробный прогон

Сначала запустить ячейку с проверкой видеокарты и ячейку установки

Если там `устройство: cpu` — видеокарта не подключена, вернитесь к A3.

## Квота и как её не тратить впустую

Тридцать часов видеокарты в неделю расходуются быстрее, чем кажется.
Два правила, выведенные из потерь:

**Либо обе карты, либо одна — но не «просим две, используем одну».**
Узел `GPU T4 x2` даёт две карты, а код с `device="cuda"` считает на первой;
вторая простаивает, а квота идёт за обе. Этап A считал эмбеддинги
5,5 часа на одной карте — на двух вышло бы около трёх. Распараллеливание
делается через `start_multi_process_pool(target_devices=["cuda:0", "cuda:1"])`
и `encode_multi_process`.

**Если параллелить не собираемся — просить одиночную карту.**
В метаданных ядра `"machine_shape": "p100"`. Узел с двумя T4 дефицитнее,
и ожидание в очереди доходило до двух часов за железом, половина
которого всё равно простаивала бы.

## Что где считать

Видеокарта нужна не всему. Разделение экономит квоту и время:

| шаг | ускоритель | почему |
|---|---|---|
| генерация запросов, эмбеддинги корпуса | **GPU T4 ×2** | 62 тысячи фрагментов через энкодер |
| выдачи по базовой нарезке, переранжирование | **GPU T4 ×2** | кросс-энкодер на 10 550 парах |
| абляции по нарезке | **None** | нарезка и BM25 — работа процессора, а плотный поиск это 211 запросов через лёгкую модель |

Сессия без ускорителя получает **больше ядер процессора** — Kaggle прямо
предупреждает об этом при включении GPU. У абляций вся нагрузка процессорная,
поэтому без карты они считаются и дешевле, и быстрее.

```bash
python3 scripts/kaggle_run.py run b --args "--only base"                    # с картой
python3 scripts/kaggle_run.py run b --no-gpu --args "--only size-256 ..."   # без карты
```

## Сколько это на самом деле занимает

Замеры первого полного прогона — `docs/raw/phase_a_timings.txt`.
**Этап A идёт 5,5 часа**, и распределено это время неравномерно:

| модель | фрагм./с | архитектура | доля времени |
|---|---:|---|---:|
| bge-m3, e5-large, USER-bge-m3 | ~47 | XLM-RoBERTa, энкодер | по 22 мин |
| Qwen3-Embedding-0.6B | 14,0 | декодер, пулинг по последнему токену | 75 мин |
| FRIDA | 7,8 | T5, скрытый размер 1536 | 134 мин |
| e5-small | 302,6 | XLM-RoBERTa, энкодер | 3,5 мин |

Две модели из шести съели 71% всего счёта. Вывод, который стоит запомнить:
**число параметров плохо предсказывает скорость — решает архитектура.**
У Qwen3-Embedding при тех же 0,6 млрд параметров вчетверо меньше скорость,
потому что это декодер с причинной маской, а не двунаправленный энкодер;
FRIDA медленнее вшестеро из-за T5 и скрытого размера 1536 вместо 1024.

Этап B гораздо легче: пятьдесят тысяч фрагментов через энкодер там уже
не гоняются, кодируются только двести запросов. Основное время уходит
на нарезку шести конфигураций и переранжирование десяти тысяч пар —
около **сорока-пятидесяти минут**.

# Этап C: обучающая выборка, dev, синтетический тест, судья

Ноутбук: [`notebooks/kaggle_phase_c.ipynb`](../notebooks/kaggle_phase_c.ipynb).
Он и есть инструкция; здесь только то, что важно знать до запуска.

**Два входа.** Датасет `ru-fin-retrieval` (код и корпус) и датасет
с набором запросов — в нём нужны `queries.jsonl`, **`split.json`**
и, для судьи, `pool_candidates.tsv`. Оба собираются командой
`make kaggle` (второй — `dist/ru-fin-queries.zip`, 200 КБ).

**Без `split.json` генерация не запустится.** Это нарочно: без сплита
вопросы попадут на акты теста, и утечку потом не отследить по метрикам.

**Токен HuggingFace подключается заново в каждой новой тетради.** Секреты
Kaggle привязываются к конкретной тетради через браузер и новым ядром
не наследуются. Однажды на этом сгорели два часа квоты: без токена
скачивание весов режется по скорости, три модели скачались за восемь минут,
четвёртая встала. Ноутбук проверяет токен первой ячейкой — до всякого
долгого прогона.

**Поэтому этап C запускается из браузера, а не `scripts/kaggle_run.py`.**
В клиенте Kaggle нет поля для секретов вообще: ядро, созданное через API,
токен получить не может — это проверено прогоном без ускорителя, то есть
бесплатно. Через API идёт только то, чему токен не нужен: этап B без
ускорителя, где веса эмбеддеров тянутся под защитой будильника из
`gpu_search.py`.

**Проверять сборку — прогоном без ускорителя.** Тот же код, те же входы,
те же импорты, модель не поднимается, квота GPU не списывается. Так
поймано, что датасет запросов уезжал без `split.json`, а `run_phase_c.py`
не доезжал на Kaggle вовсе: новая версия датасета ещё создавалась, когда
ядро уже стартовало, и оно примонтировало прежнюю. **Дожидайтесь, пока
версия датасета станет видна** (`kaggle datasets list -s ru-fin --mine -v`,
столбец `lastUpdated`), и только потом запускайте ядро.

**Порядок шагов жёсткий.**

| шаг | команда | сколько |
|---|---|---|
| замер скорости | `run_phase_c.py --probe 100` | ~20 мин с загрузкой весов |
| проба на ста актах | `--limit-acts 100 --train 20 --dev 20 --test 20` | ~10 мин |
| обучающая выборка | `--train N` (N — **по замеру**) | по замеру |
| обучающая выборка и dev | `--train 12000 --dev 300` | ~2 ч |
| третий фильтр | `--teacher-filter --filter-depth 30` | ~1,3 ч |
| тест другой моделью | `--test 400` (по умолчанию Vikhr-Nemo-12B) | ~0,5 ч |
| судья по пулу | `--judge` | 1–1,5 ч |

**Судья идёт последним, после пересчёта выдач.** Пул собирается по выдачам
всех конфигураций, а `make pool` отказывается собирать лист, пока выдачи
посчитаны по прежнему набору запросов: пул по неполным выдачам занижает
те конфигурации, которых в нём нет, и по метрикам этого не видно. Порядок:
этап B по нынешнему набору → `make pool` → перезалить датасет запросов
вместе с листом → `--judge`.

Объём обучающей выборки назначается **по замеру, а не по плану**: десять
тысяч вопросов за три часа лучше пятнадцати, которые не досчитаются
к концу сессии. Шаги независимы и готовое не пересчитывают, так что после
обрыва достаточно запустить заново; тяжёлые шаги можно разнести по двум
сессиям.

**Про T4 и типы данных.** T4 — это Turing, bf16 на нём нет. vLLM
запускается с `--dtype float16` по умолчанию, и менять это не надо:
`bfloat16` либо упадёт, либо тихо деградирует, а деградацию видно только
по качеству вопросов, то есть когда квота уже потрачена.

`queries/synthetic_dev.jsonl`, `queries/synthetic_test.jsonl`,
`queries/judge.tsv` — в `data/queries/`; `report_phase_c.json` —

# Этап D: дообучение ретривера

Два ноутбука. [`kaggle_phase_d.ipynb`](../notebooks/kaggle_phase_d.ipynb) —
весь этап, для работы руками. [`kaggle_phase_d0_commit.ipynb`](../notebooks/kaggle_phase_d0_commit.ipynb) —
только D0, для **Save & Run All**: он нужен, когда времени хватает
на подготовку и не хватает на рецепт. Недельная квота не копится,
а обновляется до полного объёма, поэтому потратить остаток на D0
выгоднее, чем сберечь.

**Оценки учителя считаются на всех картах узла.** Работа делится по парам,
связи между примерами нет, поэтому `DataParallel` даёт почти двукратное
ускорение. Просить две карты и использовать одну — худший вариант:
квота идёт за обе.

Дальше — то, что важно знать до запуска.

**Три входа.** Датасет `ru-fin-retrieval` (код и корпус), датасет
с набором запросов (`make kaggle` кладёт в него `queries.jsonl`,
`split.json`, `synthetic_train.jsonl`, `synthetic_dev.jsonl`, `qrels.tsv`,
`podvyborki.json`) и датасет с канонической нарезкой `chunks_base.jsonl.gz` —
тот же, что уехал с выдачами этапа B. Нарезку пакет `make kaggle` не несёт
нарочно: она весит около ста мегабайт и не меняется.

**Нарезка не пересчитывается.** Идентификатор фрагмента позиционный
(`акт#номер`), и при сдвиге границ он не исчезает, а начинает указывать
на другой текст: эталон обучающей выборки съехал бы молча, и модель
училась бы находить не то. `gpu_prepare.py` и `run_phase_d.py` сверяют
число фрагментов со статистикой сплита и без совпадения отказываются
считать.

**vLLM не нужен.** Языковая модель на этом этапе не запускается, поэтому
установка занимает минуту вместо пятнадцати. Нужны `sentence-transformers`
не ниже 3.0, `datasets`, `accelerate` и `mteb` для замера забывания.

**Токен HuggingFace подключается заново в этой тетради.** Правило прежнее
и причина прежняя: веса ученика и учителя тянутся с HuggingFace, а без
токена скачивание режется по скорости.

## Порядок шагов

| шаг | команда | сколько |
|---|---|---|
| проба | `gpu_prepare.py --limit 50 --depth 10` плюс `run_phase_d.py --step train --tags a-1ep --limit-train 200` | ~15 мин |
| **D0** негативы и оценки учителя | `gpu_prepare.py --depth 30` | 1–1,5 ч |
| нулевая точка | `run_phase_d.py --step baseline` | ~10 мин |
| **D1–D5** рецепт | `run_phase_d.py --step train` (дважды: сетка E строится от лучшего) | 3,5–4,5 ч |
| **D6** финал | `run_phase_d.py --step final` | ~20 мин |
| забывание | `run_phase_d.py --step forget --tags a-1ep` | ~20 мин |

## Что здесь нельзя сделать случайно

**Тест трогается один раз, на шаге `final`.** Шаг `train` считает только
по dev и без dev отказывается работать вовсе. Это не предосторожность
ради красоты: если смотреть на тест между этапами, выбор рецепта начнёт
подгоняться под него, и итоговая цифра перестанет что-либо значить.
На маке у той же ловушки своя защита — цель `make dev-metrics`, которая
считает только по dev, тогда как `make metrics` считает по всему
размеченному.

**Негативы берутся только из обучающих актов сплита.** Негатив из акта
dev или теста не портит разметку, но даёт модели увидеть текст отложенного
акта на обучении, а весь смысл сплита по актам в том, что она его
не видела. Проверка стоит в `gpu_prepare.py` и повторяется при сборке
наборов.

**Словарь заморожен.** У `multilingual-e5-small` 118M параметров, из них
96M — матрица словаря XLM-R на 250 тысяч токенов. Обучать её на шести
тысячах примеров значит переписывать представления слов, которых в выборке
нет. Обучается 22M. `apply_freeze` отказывается работать, если матрица
словаря не нашлась по имени: иначе обучение молча пошло бы по всем 118M.

**Обучение в fp32.** T4 — это Turing, bf16 на нём нет вовсе. В конфигурации
рецепта нет поля, которым можно включить половинную точность, — чтобы её
нельзя было включить случайно, взяв параметры из чужого рецепта.

**Этап C это дистилляция вместо контрастива, а не вместе с ним.** Библиотека
задаёт размер батча один на все наборы обучения, а контрастиву батч это
число негативов: учить их вместе можно только батчем 16 вместо 128, и тогда
прирост этапа мерил бы сумму «добавили дистилляцию, ослабили контрастив».
Сочетание есть, но отдельной строкой `c-oba` и с пометкой про батч 16.

**Состав этапов D и E назначается во время прогона.** «Поверх лучшего»
означает поверх состава принятого этапа, а кто им окажется, заранее
неизвестно: план этапов спрашивает журнал в тот момент, когда очередь
доходит до D. Поэтому сетку E имеет смысл запускать вторым вызовом,
когда предыдущие уже в журнале.

## Что скачать обратно

| что | куда | зачем |
|---|---|---|
| `runs/base__dense-rufin*.jsonl` | `data/runs/` | `make metrics` считает разбивку по подвыборкам |
| `train/journal.json` | `docs/raw/` | `make recipe` строит таблицу рецепта и пересчитывает вердикты |
| `train/train_prepared.jsonl` | `data/queries/` | `make check-train` проверяет отсечку негативов |
| `train/report_prepare.json`, `runs/report_phase_d.json`, `runs/zabyvanie.json` | `docs/raw/` | числа для отчёта |
| `embeddings/base/rufin/` целиком, 48 МБ | `data/embeddings/base/rufin/` | `make matryoshka` и `make latency` |
| веса лучшего этапа, ~0,5 ГБ | куда удобно | публикация на HuggingFace |

Файл `train_prepared.jsonl` стоит сохранить отдельным датасетом сразу
после D0: если сессия оборвётся, повторять полтора часа незачем —
достаточно подключить его входом следующему прогону.

# Если что-то пошло не так

| что видно | в чём дело |
|---|---|
| `устройство: cpu` | в меню **Settings → Accelerator** стоит **None**, нужно **GPU T4 ×2** |
| модель не скачивается, ошибки сети | в меню **Settings** написано **Turn on internet** — значит интернет выключен, нажать |
| нет пунктов Accelerator или Internet | не подтверждён телефон в настройках аккаунта |
| `No such file /kaggle/input/ru-fin-retrieval/...` | датасет назван иначе; заголовок должен быть ровно `ru-fin-retrieval` |
| `ModuleNotFoundError: rufin` | не выполнена ячейка `!cp -r ... /kaggle/working/` |
| сессия оборвалась посреди прогона | запустить ячейку заново, посчитанное не пересчитывается |
| `CUDA out of memory` при генерации | добавить к запуску `--generator Qwen/Qwen2.5-7B-Instruct` |
| одна модель упала, остальные посчитались | так и задумано: сбой одной не рушит прогон, смотрите строки `СБОЙ` |
| `не найдена папка embeddings этапа A` | вывод этапа A не подключён либо лежит глубже, чем ожидалось: подключите через **+ Add Input → Your Work**, а если он там есть — передайте путь явно через `--embeddings` |
| `нарезка не совпала` при выгрузке | в этой сессии другая версия `transformers`, чем была на этапе A: нарезка сдвинулась. Запускайте с тем же ускорителем и не откладывайте выгрузку надолго |
| `не найден split.json` на этапе C | не подключён датасет с набором запросов. Генерировать без сплита нельзя: вопросы уйдут на акты теста |
| `не найден pool_candidates.tsv` | пул собирается локально (`make pool`) после прогона этапа B по нынешнему `queries.jsonl` |
| vLLM падает при загрузке модели | на T4 нет bf16: `--dtype float16` (стоит по умолчанию). Если не хватает памяти — `--tensor-parallel 2` или модель в AWQ |
| `ТОКЕНА НЕТ` в первой ячейке этапа C | **Add-ons → Secrets → HF_TOKEN** в этой тетради; новым ядром секрет не наследуется |
| `нарезка разошлась со сплитом` на этапе D | не подключён датасет с `chunks_base.jsonl.gz` либо в кэше `/kaggle/working/chunks` лежит нарезка упавшего прогона. Снести кэш и положить каноническую: готовая берётся раньше, чем считается новая |
| `dev не нашёлся` на этапе D | нет `podvyborki.json` и `qrels.tsv` среди входов. Считать рецепт по тесту скрипт отказывается нарочно |
| `матрица словаря не найдена среди параметров` | версия `sentence-transformers` переименовала параметры. Обучение пошло бы по всем 118M вместо 22M, поэтому отказ, а не предупреждение |
| `сначала --step baseline` | первый этап не с чем сравнивать: нулевая точка считается отдельным шагом и попадает в журнал первой строкой |
| `порог ... не меньше глубины` | отсечка, которая ничего не отбрасывает. Уменьшить порог или убрать фильтр совсем |
| `ЗАМЕР ЗАБЫВАНИЯ НЕ СОСТОЯЛСЯ` | `mteb` не поставился или сменил устройство объекта задачи. Шаг необязательный, остальное от него не зависит |
| `CUDA out of memory` на этапе C рецепта | батч дистилляции 16 при накоплении 8; если памяти всё равно мало, уменьшить `distill_docs` в `rufin/training/config.py` |
